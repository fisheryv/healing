### 修复：手机 LAN 访问 CORS 被拒

**症状**：手机浏览器打开 `http://10.91.241.58:5173/`（vite Network 地址），提交注册 / 登录后弹 "something went wrong"。

**根因**：PB 启动时 `--origins` 只允许 `localhost:5173` / `127.0.0.1:5173` / `:5174`，LAN IP `10.91.241.58` 不在白名单。浏览器发起请求时 preflight 直接失败，前端 fetch 抛 TypeError，`errMsg` fallback 成 "Unknown error"（即 "something went wrong"）。

1. PB 重启用 `--origins="*"`（仅 dev demo，部署要改回白名单）
2. `api.js` 的 `errMsg` 区分 `TypeError`（CORS/网络）vs PB 业务错误，前者返回明确文案

**验证**：`curl -X OPTIONS ... -H "Origin: http://10.91.241.58:5173"` 返回 `Access-Control-Allow-Origin: *`。

## 关键决策

1. **手机号注册 / 登录暂不支持**：PB `users` collection 没加 phone 字段（Day 1 决定）。前端 SignUp/Login 直接拒绝并提示，避免走不通的路径。
2. **`auth.exists()` 不用在 `validate()` 里调用**：原代码想在前端做邮箱去重，但 PB 默认的 `createRule=""`（开放注册）已经会在邮箱重复时返回 400；前端同步调用 async 函数反而会引入 bug。改由 `register()` 的 `res.error` 兜底。
3. **改密码后强制重新登录**：PB 修改密码会让旧 token 失效（这是安全特性），前端直接 `auth.logout() + nav('/login')`，UI 上 toast 提示 1.2 秒。
4. **`updateProfile` 接受 dataURL**：老 Profile.jsx 的 `handleAvatarChange` 用 FileReader 生成 dataURL。api.js 把 dataURL 转成 Blob 再上传到 PB `avatar` 字段。这样不用重写前端选择头像的逻辑。
5. **`vite` 端口固定 5173**：之前 vite 自动选了 5174，被 PB CORS 拒掉。直接写死最稳。
6. **`authReady` 守卫**：浏览器刷新时 PB SDK 会从 localStorage 恢复 token，但需要 `authRefresh()` 重新校验才能拿到 model。在 `initAuth()` 完成前，user 还是 null —— 直接跳 /login 会闪屏。先显示 "Loading…"，再判断登录态。

## 修掉的 Bug

1. **`auth.exists()` 返回 Promise 在条件里永远为真**
   - SignUp.jsx 第 51 / 55 行：`else if (auth.exists(email, 'email')) errs.account = t('signup.emailExists')`
   - 之前 auth 是同步函数，现在改成 async 后，这里返回的是 Promise 对象，Promise 永远是 truthy
   - **结果**：每个邮箱注册都会被前端先弹"该邮箱已被注册"
   - **修复**：删掉这两行。重复邮箱时直接提交，PB 后端会返回 400，错误由 `formError` 展示。

2. **`auth.register` / `auth.login` 没 await**
   - SignUp.jsx 第 77、Login.jsx 第 63：`const res = auth.login(...)` —— `res` 是 Promise，`res.ok` 是 undefined
   - **结果**：登录/注册后立刻进入 `if (!res.ok)` 分支，弹一个 "Cannot read properties of undefined"
   - **修复**：加 `await`，并把所有 `res` 引用都改成从 await 里拿值。

3. **`vite` 漂移到 5174 触发 CORS 失败**
   - 5173 被其他进程占着，vite 自动选了下一个可用端口
   - PB `--origins` 白名单里没 5174，前端请求被拒
   - **修复**：`vite.config.js` 显式写 `port: 5173`，并 `pkill` 掉了占端口的旧进程。

4. **换设备登录报 "something went wrong" / "网络请求失败"**（排查耗时最长）
   - **症状**：A 设备注册的账号在 PB Admin 能看到，B 设备登录时报错
   - **根因 1：PB URL 写死 `127.0.0.1`**。`api.js` 里 `PB_URL = 'http://127.0.0.1:8090'`，B 设备的 `127.0.0.1` 指向它自己，请求根本到不了 PB。
   - **根因 2：浏览器代理拦截**。浏览器装了代理扩展（Clash / SwitchyOmega 等），把发往 LAN IP 的请求也走代理，代理连不上 → `ERR_PROXY_CONNECTION_FAILED`。连 Google Fonts 都加载不了。
   - **根因 3（真正的元凶）：`crypto.subtle` 在非安全上下文下不可用**。通过 `http://10.91.241.58:5173`（LAN IP 的 HTTP）访问时，浏览器认为是非安全上下文，`crypto.subtle` 是 `undefined`。`sha256()` 调 `crypto.subtle.digest()` 抛 `TypeError`，被 `errMsg` 误归类成"网络请求失败"，严重误导排查方向。
   - **修复**：
     1. `vite.config.js` 加 proxy：`/api` 和 `/_` 转发到 `http://127.0.0.1:8090`，让浏览器只请求 vite 同源地址，不直连 PB
     2. `api.js` 的 `resolvePbUrl()` dev 环境改用 `window.location.origin`（同源），让 vite proxy 接管。**不能用裸 `/`**，否则 SDK 拼出的 URL 会变成 `//api/...` 被当成协议相对路径
     3. `sha256()` 加兜底：`crypto.subtle` 不可用时退回非加密哈希（仅 dev 用，生产必须 HTTPS）
     4. `errMsg()` 改进：`TypeError` 不再一律报"网络错误"，会带上真实 `message`，避免误诊
   - **教训**：`TypeError` 不一定是网络问题，也可能是 JS 运行时错误（如 API 不可用）。`errMsg` 不该把所有 `TypeError` 都归为"网络请求失败"。

5. **`pb.files.getUrl()` deprecation**
   - PB SDK 0.27 把 `getUrl` 改名成 `getURL`，console 会打印 deprecation 警告
   - **修复**：`api.js` 里 `pb.files.getUrl` → `pb.files.getURL`

## 排查指南：前端请求 PB 失败时怎么办

以后再遇到"网络请求失败""something went wrong"这类报错，按这个顺序排查（从最常见到最隐蔽）：

### 第 1 步：确认 PB 在跑

```bash
lsof -nP -iTCP:8090 -sTCP:LISTEN
# 应看到 pocketbase 进程监听 *:8090 或 127.0.0.1:8090
```

没在跑就启动：
```bash
cd backend && pocketbase serve --http=0.0.0.0:8090 --origins="*"
```

### 第 2 步：确认 vite dev server 在跑、端口对

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
```

- 没在跑 → `cd src && pnpm dev`
- 跑在别的端口（5174/5176...）→ 说明有多个 vite 进程冲突，`pkill -9 -f vite` 全杀后重启
- **改过 `vite.config.js` 后必须重启 vite**，HMR 不会重载 config

### 第 3 步：确认 vite proxy 生效

```bash
# 经 vite 代理打 PB，应该返回 200 + JSON
curl -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:5173/api/collections/users/records \
  -H "Content-Type: application/json" \
  -d '{"email":"proxytest@test.com","password":"Abcd1234","passwordConfirm":"Abcd1234","nickname":"t"}'
```

返回 200 → vite 代理正常，问题在浏览器端
返回失败 → 检查 `vite.config.js` 的 `proxy` 配置

### 第 4 步：浏览器 Console 看真实错误

**关键**：`errMsg` 现在会带上真实 `message`，但如果是 `TypeError` 仍可能误导。最可靠的方法是**临时在 `api.js` 的出错位置加 `console.error(e)`**，看完整 error 对象。

常见 `TypeError` 根因：
- `Failed to fetch` → 真的是网络/CORS/代理问题
- `Cannot read properties of undefined (reading 'digest')` → `crypto.subtle` 不可用，非安全上下文（见第 6 步）
- `Cannot read properties of undefined (reading ...)` → 其他 JS 运行时错误，看堆栈定位

### 第 5 步：检查浏览器代理

**症状**：Console 里 `net::ERR_PROXY_CONNECTION_FAILED`，连 Google Fonts 都加载不了。

- Chrome：设置 → 系统 → 关闭代理，或禁用 SwitchyOmega / Clash 等扩展
- 或者直接用**无痕窗口**测试（无痕模式默认不走扩展代理）
- 手机测试：确认手机没开 VPN

### 第 6 步：检查安全上下文（`crypto.subtle`）

**症状**：通过 LAN IP（`http://10.91.241.58:5173`）访问时注册失败，但 `localhost` 访问正常。

**原因**：`crypto.subtle`（Web Crypto API）只在 HTTPS 或 `localhost` 下可用。LAN IP 的 HTTP 是非安全上下文，`crypto.subtle` 为 `undefined`。

**验证**：浏览器 Console 执行 `crypto.subtle`，返回 `undefined` 就是这个问题。

**解决**：
- dev：用 `http://localhost:5173` 访问（不用 LAN IP）
- 手机测试：要么忍受 `sha256` 兜底哈希（已实现，dev 够用），要么给 vite 配 HTTPS（`server.https`）
- 生产：必须 HTTPS

### 第 7 步：用 Console 直接测 SDK

把 `pb` 和 `auth` 暴露到 window（`api.js` 里 `window.pb = pb`），然后在 Console 执行：

```js
// 测读
pb.collection('users').getList(1,1).then(r=>console.log('OK',r.items.length)).catch(e=>console.log('ERR',e.message))

// 测写 + 登录
auth.register({email:'t@t.com',password:'Abcd1234',nickname:'t',recoveryQuestion:'q',recoveryAnswer:'a'}).then(r=>console.log(r))
```

能直接定位是 SDK 哪一步挂了。排查完记得删掉 `window.pb = pb`。
